# Cineo — Source-level repository research for automated cinematic editing

**Date:** 2026-10-20  
**Scope:** Native Mac screen capture → non-destructive automated / assisted / manual video edit → headless CLI → playable local export.  
**Evidence classes:** **CODE** = implementation file read; **DOCS** = source maintainer's claim; **META** = GitHub repository metadata at the time of research; **CI** = Cineo's previous compile-only benchmark; **NOT VALIDATED** = no real-Mac reproduction/perceptual benchmark was performed during this research. Distinguish these rigorously.

**Executive recommendation:** **Reuse concepts and, after provenance/CLT/license verification, the smallest feasible subset of Orbit's Core Image rendering stack; keep CineoProject + CineoDirector + CineoEditPlanner as the canonical edit model; borrow CLI/service patterns from OpenScreen, deterministic idle-selection from Auto-Editor and structured agent-tool boundaries from Palmier. Do not fork an Electron/Rust editor or integrate an AGPL/GPL compositor into Cineo by accident.** The standalone CLT-only native app needs an *actual* first export (not another architecture-only spike).

## Five proven implementation patterns to adopt

### 1. Immutable scene plan and one frame evaluator (Orbit; CineScreen)

**Pipeline:** `CineoManifest` + source media + `TimeMap` + validated `EditDecision` → immutable `CineoRenderPlan` → `evaluateScene(outputTime)` → **one frame compositor** → preview or encode.

- **Orbit:** `RenderPlan` precomputes camera/cursor/overlay resources when project changes; `FrameRenderer.draw` uses shared `CIImage` transforms for rendering. It decouples editing from heavy frame calculations; the precomputation layer must rebuild after relevant mutations.
- **CineScreen:** `FrameCompositor.encode` is reused *directly* by MTK preview and offline export adapters. Frame acquisition and GPU lifetime differ, but pass order and state are the same. This is the stronger exact-parity pattern; see also CVPixelBuffer retention.
- **ArcShot:** custom `AVVideoCompositing` handles per-frame Core Image rendering, but their editor documentation describes an approximate overlay preview. **Do not replicate that divergence**; use identical scene evaluation and ideally identical rendering for preview/export, measured on golden frames.

**Decision:** build a **CLT-compilable Core Image/AVFoundation minimum** first, using Orbit's `RenderPlan/FrameRenderer` as a migration candidate. Ship neither a second compositor nor an independently coded SwiftUI mock pretending to be export-quality preview.

### 2. Separate input activity, editorial intent and actual camera motion (Orbit; ArcShot; CineoDirector)

**Pipeline:** opt-in time-coded **events** → temporal/spatial click clusters/dwell → `AttentionTarget` with source/time/confidence → suggested `CameraShot` (reason + range + framing) → accepted/manual/rejected decisions → deterministic spring camera state evaluated per output frame.

- **Do not auto-zoom every click**: group bursts, reject duplicates, enforce max shots/minute, start with wide context, hold long enough to read the result.
- Orbit's critically damped spring sampled at **120 Hz**, interpolated at frame time, models natural pan/zoom. Zoom values integrate logarithmically. Existing CineoDirector already has clustering, shot rate budgets and **Subtle/Balanced/Dynamic** presets — **extend this** rather than introduce parallel heuristic planners.
- ArcShot's `ZoomIntentPlanner` splits activity classification from intent and camera motion; manual zoom intervals suppress suggested motion. Implement the *idea* in our code; ArcShot's license is restricted.
- Suggested edits have **stable IDs and reason codes**, are regenerable and separable from overrides. Never mutate the source and never promote a tentative semantic guess into a factual claim.

**One gap to solve:** the already captured 25 s MP4 has **no separately synchronized cursor/click sidecar**. It supports *style and manually placed zooms*, not reliable click-derived zoom suggestions. If an old recording has a burned-in cursor, rendering an extra cursor overlay creates a double cursor: detect availability and disable synthetic cursor by default.

### 3. One input clock and edit timebase (Orbit; OpenScreen; CineScreen)

- Use first actual video PTS as zero and calibrate monotonic clock for pointer callbacks; never use `Date()` as timeline truth. Record capture window/display geometry, Retina scale and Y-axis convention explicitly.
- Store source PTS independent of trims/speeds; map `outputTime ↔ sourceTime` through `CineoProject.TimelineMapper`. Snapshot `SceneState` with a **single sampled time** so cursor/zoom/click events match decoded pixels.
- OpenScreen's `timelineSegments.ts` is a strong reference for normalized, nonoverlapping keep/speed segments that audio/video both use. Handle adjacent, nested and overlapping segments and speed changes with adversarial fixtures.
- When source cursor is hidden and redrawn, overlays must apply identical crop+camera transforms; validate near all four screen corners, non-primary monitors and window titlebar offsets.

### 4. Explicit local jobs and CLI/UI shared execution (OpenScreen; Palmier; Auto-Editor)

- **OpenScreen:** CLI launches a hidden Electron renderer but reuses the actual GUI recording/export stack; publishes JSON progress, frame counts, phase and ETA. **Borrow the job interface, not the Electron dependency.**
- **Palmier:** one validated `ToolExecutor` exposed to both the in-app agent and MCP; project binding/active-project checks, export queue and job cancellation. **Borrow tool semantics, not the GPL implementation.**
- Cineo should expose `validate / plan / plan-inspect / render / export-status / cancel` through a **Swift service** called by native UI and CLI. CLI must remain a real **non-GUI SwiftPM executable**.
- Job state: `queued → preparing → rendering(currentFrame,totalFrames) → verifying → promoting → complete|failed|cancelled`. `totalFrames` derives from validated timeline and output fps; **do not invent remaining time**; report ETA only after observed throughput and label it an estimate.
- Nonzero exit on invalid source/plan; no overwrite unless explicitly requested; JSON-line progress on machine-readable stdout, detailed diagnostics on stderr; avoid embedding paths, secret UI content, user input in collected logs.
- **Later:** an optional agent/MCP boundary that creates and validates **the same plan**; per-operation allowlisting, project-scoped writable state, no local HTTP server enabled by default.

### 5. Export recovery and real-media acceptance (CineScreen; ArcShot; OpenScreen; Auto-Editor)

- Stage export beside final destination or in safe container, validate expected codec/frame rate/frame size/duration/track, then promote with a properly tested atomic replacement strategy that **does not first delete the user's destination**. CineScreen illustrates side-by-side temporary promotion; ArcShot validates before promotion but explicitly removes an existing destination before move — **do not copy that destructive edge case**.
- Preserve first failure cause and treat subsequent cancellation/disconnection as teardown noise.
- Preview may be faster/lower resolution, but golden-frame geometry, cursor offsets and duration mapping must agree with exports. Document any intentional color/blur-quality differences.
- Rule-based silence/motion cutting from Auto-Editor is **optional** and only after we capture audio or can independently establish true inactivity. With the current **silent** capture, silence detection would erroneously classify all 25 seconds; do NOT default to silence cuts.
- Prioritize no-click, static-with-loading-animation, rapid-click and dense-UI fixtures in addition to the happy path.

## Critical CLT-only renderer decision (not optional)

The User explicitly rejects mandatory `Xcode.app`. Apple Command Line Tools supply Swift and the macOS SDK but **not necessarily the Metal shader compiler**, which may require optional Metal Toolchain/Xcode. Existing Cineo upstream [CI matrix](../research/p0-native-build-results.md) used **Xcode 26.6**, not the standalone CLT. See [Apple Metal Toolchain documentation](https://developer.apple.com/documentation/Xcode/downloading-and-installing-additional-xcode-components) and [a real CLT-only failure example](https://github.com/OpenCut-app/OpenCut/issues/839). Native `Metal.framework` runtime availability does **not** prove compiling `.metal` files without full Xcode.

**Plan B1 — required gate:** prototype `CineoScene` as **Core Image + AVFoundation**, using existing SwiftPM macOS SDK; exact scene state must be pure/testable. Export real 25 s H.264 with background, padding, safe crop, one manual spring zoom.

**Plan B2 — independent optional experiment:** probe `xcrun --find metal` and compile one trivial `.metal` shader on the **same CLT-only CI runner**; if unavailable or a separate Xcode download becomes necessary, **fail the Metal experiment**, not the product roadmap. A runtime Metal shader compilation strategy may be investigated separately but must demonstrate deterministic resource/launch behavior and a valid licensing/distribution path.

**Plan B3 — benchmark (only if B2 passes):** compare exact scene on CPU/RAM/GPU, per-frame p50/p95, encode throughput and preview/export visual differences. Switch renderers only for measurable improvement and while preserving the same frame evaluator. No dual competing compositor architectures.

## Code-reuse governance and detailed feasibility experiments

1. **No immediate wholesale source import.** Orbit has already been conditionally selected in [ADR-0001](../decisions/0001-native-foundation.md) as the P1 reference and successfully compiled *with full Xcode*. Now prove the smallest CoreImage+AVFoundation `RenderPlan/FrameRenderer` slice can actually be built in the standalone CLT-only Cineo target. Take one small end-to-end test before migrating multiple editor classes.
2. **Per-file reuse ledger required:** source URL/commit/file, copyright holder, actual license/NOTICE, dependency/asset provenance, changed paths, tests, upstream sync path, and why integration is safe. Do not copy text, icons, bundled fonts, asset files or restricted code by "inspiration".
3. **Measure alternative implementations on identical inputs:** Orbit-based CI/Core Image candidate vs minimal in-house Core Image proof vs CineScreen Metal only if compiler gate passes. Two resolution cases: original 1512×982 display capture and output 1920×1080 / 1080×1920; color-space/Retina behavior defined; evaluate 3/10/25/60 s and one 4K fixture when practical.
4. **Check pixel quality and human utility:** verify H.264 duration/dimensions/PTS, source preservation, center/corner framing, cursor parity, image/text readability, edit velocity, project reopen, copy-safe export, and accepted vs rejected suggestions. A successful compile is not a rendered video.
5. **Separate new work from capture lifecycle:** draft PR #44 fixes ScreenCaptureKit finalization and LaunchServices identity; keep that runtime stabilization distinct from compositing. Never reintroduce `removeRecordingOutput()` before `stopCapture()` when packaging the editor.
6. **No Xcode dependency or mandatory third-party binary:** `swift build` from `/Library/Developer/CommandLineTools` is acceptance condition. Optional benchmark helpers must not be required for basic Cineo installs or running finished application.

## Recommendation + immediate branch order

**No wholesale rewrite, no six incompatible PRs.** Start with one **contract-and-provenance PR** (v0 scene/effect schema, render job, identity policy, Orbit file reuse assessment), then split independent tracks; the dedicated integration owner alone touches the Cineo app root. Prioritize **B Core Image renderer + A project bridge + F fixture/probe + E Swift CLI** in parallel, while **C mouse events** and **D UI** work from frozen interfaces.

**First G1 demo:** import the validated 25-second silent MP4 → apply "Clean" canvas frame and one manually-selected camera shot → render edited MP4 from Cineo native CLI and verify it is visually different, decodable, original source unchanged. **G2:** make genuine click-driven first-cut on a newly recorded source with opt-in telemetry and per-suggestion approval. **G3:** export same `.cineo` + plan from CLI and UI, golden-frame parity. **No LLM/semantic feature work before these pass**.

This research is a source-level feasibility review, **not** a claim that we successfully built/ran all upstreams, integrated their source into Cineo or verified native export results in this turn.
